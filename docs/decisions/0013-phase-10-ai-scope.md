# ADR 0013: Phase 10 AI scope — adapters, insight types, and the Anti-Distraction Guard

**Status**: Accepted
**Date**: 2026-09-03

## Context

Blueprint §C schedules "AI Assistant (Morning Brief, Evening Review, Weekly Coach, Planning Assistant, Decision Assistant, Anti-Distraction Guard)" across "Phase 10–12, explicitly scheduled" — not all six sub-features are mandated to land in Phase 10 specifically. §M.1 names three adapters (`AnthropicAdapter`, `OpenAIAdapter`, `LocalModelAdapter`) with only the local one qualified as a stub ("interface allows it later, not implemented now" — §C's DO NOT BUILD YET list). §M.3's Action Model defines READ/SUGGEST/WRITE tiers generically, without prescribing which specific `ai_insights.type` values must exist at MVP.

This environment also has no real `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` configured (both blank in `.env.local`), so live success-path testing against a real provider is not possible from this sandbox — the same category of constraint already documented for Phase 2's auth E2E test (`docs/ARCHITECTURE.md`'s "Known limitation of this development session").

## Decision

- **Adapters**: `AnthropicAdapter` and `OpenAIAdapter` are both real implementations (`@anthropic-ai/sdk`, `openai`), selected via `getAIProvider()` (deployment `AI_PROVIDER` env var, overridable per-user via `settings.ai_provider`). `LocalModelAdapter` is a stub that throws a clear "not implemented" error — per §C, this was never in scope for Phase 10.
- **`ai_insights.type`**: scoped to exactly two values this phase — `plan_breakdown` (Planning Assistant) and `suggest_reschedule` (Weekly Coach). The migration's check constraint lists only these two; adding a new insight type is a new migration, not a payload convention layered on top of an open-ended `text` column.
- **Five of six AI Assistant sub-features ship this phase**: Morning Brief and Evening Review (READ tier — a single generated message, no insight), Weekly Coach and Planning Assistant (SUGGEST tier — may produce an insight), Decision Assistant (READ tier — advisory text only, deliberately no insight or write path, since "which decision to make" isn't a structured change to approve). Freeform chat (not one of the blueprint's six but implied by the AI Coach screen spec in §F) also ships, sharing the same thread/message infrastructure.
- **Anti-Distraction Guard is deferred**, not built this phase. Blueprint §D.2 names it as a third trigger for the existing Active Project conflict modal ("later, Phase 10... when the AI's Anti-Distraction Guard detects the same condition"), but doesn't specify what continuously monitors for "the same condition" outside an explicit user action — every other Phase 10 AI feature is either read-on-demand (a button the user clicks) or reactive-on-approval (a suggestion the user acts on); the Guard as described implies proactive, unprompted detection, which is a different shape of feature (closer to blueprint §M.4's Automation engine, explicitly "design only, not built until Phase 11") than anything else in this phase.
- **Live provider testing is PENDING**: the SUGGEST→Approve→write path is verified end-to-end against a seeded (not AI-generated) `ai_insights` row and pure-logic tests of the exact FormData shape `approveInsight()` builds (`tests/ai-insight-write-path.ts`); the Context Engine's data-assembly and prompt formatting are verified directly (`tests/ai-context-format.ts`); RLS isolation on all three new tables is verified against real Postgres. What is **not** verified in this sandbox: an actual chat completion or structured completion succeeding against a real Anthropic/OpenAI key, and the "AI Coach is unavailable right now" degraded-mode UI rendering in a live authenticated browser session (this sandbox cannot complete a real login at all — the same `*.supabase.co` egress block documented for Phase 2). Every provider call is wrapped in try/catch that degrades to a threadless-reply state rather than crashing (verified by code review, not a live run) — update this ADR once a live key is available and both are exercised for real.

## Consequences

- A future phase adding a new insight type (e.g. `flag_overload` for a real Anti-Distraction Guard) needs a migration to extend `ai_insights.type`'s check constraint, plus a new discriminated variant in `features/ai/types.ts`'s `AiInsightPayload` union and a new branch in `approveInsight()` — the pattern is established, not the enumeration.
- Decision Assistant threads support continued freeform chat (same `ChatInput`/`sendChatMessage` as a freeform thread) but never write anything — if a future phase wants the AI to draft `actualOutcome`/`lesson` text for `resolveDecision()` to prefill, that's a new SUGGEST-tier insight type, not a change to Decision Assistant's current READ-only contract.
- The Local model adapter remaining a stub means selecting `local` in Settings' AI Provider dropdown (or `AI_PROVIDER=local`) always fails with a clear error — expected, not a bug, until a future phase implements it.
